# FirstLook 단계별 개발 계획

> 기준 문서: `service-design-rule.md`, `TECH-AGENTS.md`
>
> 이 계획은 서비스 규칙이 바뀌면 다시 검토한다. 제품 규칙과 충돌할 경우 서비스 설계 규칙을 우선한다.

## 현재 상태

- 현재 구현: HTML/CSS/Vanilla JavaScript 기반 SPA 프로토타입
- 현재 데이터: 브라우저 localStorage와 샘플 이미지
- 목표: 사진 기반 첫인상 질문·투표·결과·운영 흐름을 갖춘 안전한 웹 서비스
- 핵심 제약: P1 정책이 미결정이므로 실제 계정, 이미지 업로드, 공개 피드, 투표 API는 아직 구현하지 않는다.

## 전체 로드맵

| 단계 | 목표 | 선행 조건 | 완료 산출물 |
| --- | --- | --- | --- |
| 0 | P1 제품·안전 정책 확정 | 없음 | 확정된 정책과 결정 기록 |
| 1 | React 기반 프론트엔드 전환 | 단계 0 없이 가능 | Vite·React 앱, 컴포넌트 구조, 목업 데이터 |
| 2 | 디자인 시스템·핵심 UX 정비 | 단계 1 | 접근 가능한 Feed·Upload·Ranking·Profile |
| 3 | 백엔드 기반 구축 | 단계 0 완료 | 인증, DB, 이미지 저장소, API 기반 |
| 4 | 게시물·검토·투표 기능 구현 | 단계 3 | 안전한 업로드, 검토, 1인 1투표, 집계 |
| 5 | 결과·랭킹·운영 기능 구현 | P2/P3 정책 완료 | 분석 화면, 랭킹, 신고·운영 도구 |
| 6 | 검증·배포·베타 운영 | 단계 5 | 테스트, 관측성, 운영 환경, 베타 출시 |

## 단계 0 — P1 정책 결정

### 목표

실사용자 데이터와 사진을 다루기 전에 서비스의 권한·안전·운영 경계를 확정한다.

### 결정 순서

| 순서 | 결정 항목 | 결정해야 할 질문 | 이후 열리는 개발 |
| --- | --- | --- | --- |
| 0-1 | 공개 범위와 계정 접근 | 누가 가입·열람·투표할 수 있는가? 로그인 방식은 무엇인가? | 인증, 보호 라우트, 피드 API |
| 0-2 | 익명성·차단 정책 | 업로더·평가자의 핸들은 어디까지 공개되는가? 차단 시 무엇을 숨기는가? | User/Profile, 차단, 감사 로그 |
| 0-3 | 사진 권리·연령 정책 | 본인 사진만 허용하는가? 최소 연령과 타인·미성년자 사진의 처리 기준은 무엇인가? | 업로드 동의, 콘텐츠 검증 |
| 0-4 | 검토·신고 흐름 | 자동·사람 검토 순서, 신고 유형, 보류·삭제·이의 절차는 무엇인가? | Post 상태, ModerationCase, 운영자 API |

### 완료 기준

- 각 항목이 `service-design-rule.md`의 우선순위 표에서 구체적 정책·날짜와 함께 완료 상태가 된다.
- `TECH-AGENTS.md`가 해당 정책에 따른 인증·데이터·API 규칙으로 동기화된다.
- P1 기준을 만족하지 못한 기능은 목업 상태로만 남긴다.

---

## 단계 1 — React 기반 프론트엔드 전환

### 목표

현재 단일 HTML/JavaScript 프로토타입을 유지보수 가능한 React 컴포넌트 구조로 옮긴다.

### 작업

1. Vite + React + JavaScript 프로젝트를 생성한다.
2. ESLint, Prettier, Vitest, React Testing Library를 설정한다.
3. 기존 정적 이미지와 CSS 토큰을 이전한다.
4. 라우트와 페이지를 `Feed`, `Upload`, `Ranking`, `Profile`로 분리한다.
5. 카드, 투표 버튼, 카테고리 필터, 토스트, 하단 내비게이션을 재사용 컴포넌트로 분리한다.
6. localStorage 데이터는 개발용 목업 어댑터로만 유지한다.

### 완료 기준

- 기존 프로토타입의 네 화면과 카드 탐색·필터·목업 투표·업로드 미리보기가 React에서 동일하게 동작한다.
- 페이지·컴포넌트·스타일이 `TECH-AGENTS.md` 구조를 따른다.
- 기본 lint, 빌드, 컴포넌트 테스트가 통과한다.

---

## 단계 2 — UX·접근성·목업 API 정비

### 목표

백엔드 없이도 실제 서비스 전환에 적합한 사용자 경험과 API 경계를 준비한다.

### 작업

1. loading, empty, error, permission, under_review 상태 UI를 설계한다.
2. 키보드 탐색, 포커스, 색상 대비, 이미지 대체 텍스트를 검증한다.
3. Post, Vote, Aggregate, Report의 JSDoc 데이터 계약과 목업 API를 작성한다.
4. 업로드 폼의 형식·용량·질문 입력 검증을 클라이언트에서 제공한다.
5. 표본 부족, 검토 중, 비공개·삭제 상태의 결과 문구를 비판단적 언어로 정리한다.
6. API 실패와 재시도 UX를 TanStack Query 경계에 맞춰 설계한다.

### 완료 기준

- 네트워크·권한·빈 상태에서 사용자가 다음 행동을 이해할 수 있다.
- 목업 데이터가 실제 API 계약을 따르며, 페이지가 서비스 계층에만 의존한다.
- 접근성·폼·오류 상태 테스트가 추가된다.

---

## 단계 3 — 백엔드 기반 구축

### 목표

실사용자·권한·사진·영구 데이터를 안전하게 처리할 기반을 만든다.

### 작업

1. Node.js + Fastify 서버, 환경 변수 검증, 공통 오류 형식을 구성한다.
2. PostgreSQL + Prisma로 User, Post, Vote, Aggregate, Report/ModerationCase, AuditLog 스키마를 만든다.
3. 인증과 역할(일반 사용자·운영자·관리자), 보호 API, 세션 만료 처리를 구현한다.
4. S3 호환 저장소와 짧은 수명 서명 URL 기반 업로드 흐름을 구현한다.
5. 이미지 형식·크기·EXIF 처리·접근 제어·삭제 작업을 구현한다.
6. Redis 기반 속도 제한과 비동기 작업 큐의 기반을 둔다.
7. 개발·스테이징·운영 환경, 비밀 관리, 로그·오류 추적을 분리한다.

### 완료 기준

- 인증된 사용자가 자신의 리소스에만 접근할 수 있다.
- 비밀값과 원본 이미지가 클라이언트·저장소·로그에 노출되지 않는다.
- DB 마이그레이션, 백업·복구 절차, API 인증·권한 테스트가 준비된다.

---

## 단계 4 — 게시물·검토·투표 기능

### 목표

사진 등록부터 안전한 공개, 유효 투표 집계까지의 핵심 루프를 완성한다.

### 작업

1. `draft → submitted → under_review → published → archived/deleted` 상태 전이를 API와 UI에 구현한다.
2. 업로드 동의, 질문·카테고리 검증, 이미지 검사, 검토 대기 UI를 구현한다.
3. 운영자 검토 화면과 신고 생성·처리 흐름을 구현한다.
4. 카드당 사용자 1표 제약, idempotency key, 서버 시간, 속도 제한을 구현한다.
5. Aggregate를 서버에서 계산하고, 결과 화면에 유효 표본·긍정률을 표시한다.
6. 차단·삭제·검토 상태의 카드가 피드와 투표에 미치는 영향을 테스트한다.

### 완료 기준

- 정책을 통과한 콘텐츠만 피드에 노출된다.
- 같은 사용자가 동일 카드에 중복 유효 투표를 만들 수 없다.
- 업로더는 자신의 게시물·결과·삭제 상태를 확인할 수 있다.
- 운영자는 신고와 상태 변경을 감사 로그와 함께 처리할 수 있다.

---

## 단계 5 — 결과·랭킹·운영 기능

### 선행 결정

- P2: 투표 변경·최소 표본·이상 투표 처리
- P2: 삭제·탈퇴·백업 보존 기간
- P3: 랭킹 최소 표본·기간·동점·제외 기준

### 작업

1. 결과 화면에 표본 수, 긍정률, 신뢰도 설명, 카테고리 요약을 제공한다.
2. 확정된 랭킹 정책에 맞는 조회·캐시·재계산 작업을 구현한다.
3. 업로더 프로필과 게시물 관리 화면을 구현한다.
4. 운영자용 신고 큐, 상태 이력, 검색·필터, 처리 지표를 구현한다.
5. 핵심 지표(등록·첫 투표·신고·검토 시간·오류율)를 수집한다.

### 완료 기준

- 랭킹과 결과가 서버 집계·정책 기준에서 일관되게 계산된다.
- 운영자가 안전 이슈를 추적·처리할 수 있다.
- 사용자 문구가 결과를 사람의 가치 판단으로 오해하게 만들지 않는다.

---

## 단계 6 — 검증·배포·베타 운영

### 작업

1. 단위·통합·E2E·권한·업로드·속도 제한 테스트를 CI에 연결한다.
2. 성능, 오류율, 보안 이벤트, 큐 실패, 스토리지 비용의 관측·경보를 설정한다.
3. 개인정보 처리방침, 이용약관, 콘텐츠 정책, 신고·삭제 안내를 서비스에 노출한다.
4. 스테이징에서 운영자·대표 사용자 시나리오를 검증한다.
5. 제한된 베타로 시작해 신고율·검토 시간·오류를 관찰하고 개선한다.
6. 복구·롤백·장애 대응 절차를 문서화하고 모의 점검한다.

### 완료 기준

- 핵심 사용자 여정과 권한·안전 시나리오가 자동 또는 재현 가능한 테스트로 검증된다.
- 운영자와 사용자 모두가 정책·신고·삭제 경로를 이해할 수 있다.
- 배포·롤백·데이터 복구 절차가 검증된다.

## 진행 관리 규칙

- 각 단계의 착수 전, `service-design-rule.md`의 P1/P2/P3 결정 상태를 확인한다.
- 서비스 규칙이 바뀌면 `TECH-AGENTS.md`와 이 계획의 영향 항목을 같은 작업 흐름에서 갱신한다.
- P1 또는 현재 단계에 필요한 P2가 미결정이면 `🚨 개발 결정 필요` 알림을 먼저 표시하고, 해당 기능 구현을 시작하지 않는다.
- 단계 완료 시 완료 기준을 검증한 결과와 남은 위험을 이 파일의 변경 기록에 남긴다.
